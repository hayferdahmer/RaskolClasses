# Class Lock 1.16.0 — контракт LuckPerms

## Источник истины

Класс персонажа хранится в LuckPerms как группа вида `class_<name>`. Каноническая группа должна быть одновременно:

1. единственной эффективной class-группой пользователя;
2. его фактической primary group, возвращаемой LuckPerms `User#getPrimaryGroup()`.

Примеры допустимых групп: `class_warrior`, `class_hunter`, `class_priest`, `class_mage`, `class_rogue`, `class_warlock`.

RaskolCore также определяет класс по primary group. Поэтому RaskolClasses не выбирает произвольную наследуемую class-группу: оба плагина должны видеть один и тот же результат.

## Разрешение класса

`ClassGroupResolver` анализирует primary group и все эффективные наследуемые группы:

- нет групп `class_*` — игрок пока без класса;
- ровно одна известная `class_*` и она совпадает с primary — класс разрешён;
- несколько class-групп — конфликт;
- class-группа есть, но не является primary — конфликт;
- неизвестная группа с префиксом `class_` — конфликт.

При конфликте `ClassProvider` возвращает `null`; он не пытается угадать класс по порядку наследования и не обходит конфликт через Core hook. LuckPerms backend пишет одно предупреждение на игрока до устранения конфликта. Spec 2.0 сохраняет основную специализацию и ранги, пока класс не разрешён, но временно отключает ролевые пассивки.

## Назначение и смена класса

В RaskolClasses нет команды `/rc set <class>`. `/rc set` предназначена для сетов экипировки. Первичное назначение класса выполняется серверным процессом/администратором через LuckPerms: игроку назначается ровно одна группа `class_<name>`, которая становится primary.

Обычная смена класса вне игровых сценариев выполняется администратором через LuckPerms. Группа — источник истины; отдельная копия выбранного класса в `characters.yml` не создаётся.

## Замена группы Фолиантом Душ

Фолиант использует `ClassProvider.replaceClassGroup`:

1. проверяет наличие целевой группы, создаёт её при отсутствии;
2. если у целевой class-группы нет веса, выставляет вес не ниже максимального веса существующих class-групп;
3. загружает пользователя через LuckPerms API;
4. удаляет прямые class-группы пользователя, добавляет целевую и задаёт её как stored primary group;
5. сохраняет пользователя и проверяет фактический результат через тот же resolver;
6. если итоговая группа не стала единственной primary class-группой, восстанавливает исходные прямые class-группы и primary group, а переход отклоняется.

Console fallback намеренно не используется: он не даёт надёжно подтвердить фактический primary group и мог оставить игрока с расходящимися состояниями.

## Требования к конфигурации LuckPerms

LuckPerms `User#getPrimaryGroup()` зависит от настройки расчёта primary group. При режиме `parents-by-weight` stored primary, установленный через API, может не совпадать с фактическим primary; вес группы должен обеспечивать требуемый результат. Плагин проверяет фактический результат и откатывает операцию, если целевая группа не стала primary.

Не назначайте игроку две группы `class_*`. Не вкладывайте одну class-группу в другую группу, которая выдаётся игрокам как дополнительная роль: такая схема создаёт конфликт, даже если одна class-группа указана напрямую.

## Диагностика

- `/rc debug` — проверить определённый класс и источник.
- `/lp user <игрок> info` — проверить primary group и членство.
- `/lp group <class_name> info` — проверить вес и наследование группы.

Если resolver сообщает конфликт, оставьте игроку одну эффективную class-группу и убедитесь, что она является фактической primary group.
