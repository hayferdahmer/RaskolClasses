# RASKOL Archivist — аудит SafeStorage и жизненного цикла игровых данных

## Статус документа

- Репозиторий: `hayferdahmer/RaskolClasses`
- Целевая платформа: Paper 26.2 / Java 25
- Документ: архитектурный аудит и контракт автоматизированных проверок
- PR с аудитом: #60
- SafeStorage fail-closed: реализован и объединён через PR #62
- Объединение профиля и специализации: PR #45 объединён в main (squash commit `0b8982c2690564d38f91031287ee7847817e0796`)
- Storage Integrity & Maintenance: целевая игровая подсистема; реализация ещё предстоит

Документ описывает фактическое состояние main после объединения PR #45 и отдельно отделяет реализованные storage-механизмы от будущей подсистемы обслуживания. Наличие требований или тестового контракта в этом документе не означает, что будущая функциональность уже реализована.

## 1. Архитектурные границы: три разных уровня

### 1.1 SafeStorage — runtime-механизм хранения

SafeStorage отвечает за безопасную загрузку и атомарную запись отдельных YAML-файлов:

- различает новое, успешно загруженное, восстановленное, повреждённое хранилище и I/O-ошибку;
- проверяет основной файл и резервные копии в определённом порядке;
- сохраняет повреждённые копии в карантине;
- не разрешает молча заменить существующие повреждённые данные пустой конфигурацией;
- валидирует YAML-снимок перед заменой файла.

Это библиотечный механизм, используемый игровыми storage-компонентами. Он не является планировщиком обслуживания, системой резервного копирования всего сервера или автоматическим очистителем данных.

### 1.2 RASKOL Archivist — CI-аудитор

Archivist — автоматизированный контур проверки гарантий хранения. Он должен проверять код, тесты, миграционные сценарии и архитектурные инварианты до принятия изменений.

Archivist CI:

- запускает и анализирует тесты SafeStorage;
- проверяет сценарии восстановления main / .tmp / .bak;
- проверяет fail-closed поведение и сохранность исходников;
- проверяет quarantine metadata и SHA-256;
- тестирует миграции профилей и специализаций на изолированных fixtures;
- проверяет порядок записи unified snapshot, обновления backup и архивации legacy-источников;
- проверяет, что неизвестная структура или неподдерживаемая схема не трактуются как пустые данные;
- формирует отчёт о проверенных гарантиях и проваленных сценариях.

Archivist CI не обслуживает живые игровые хранилища, не удаляет файлы сервера и не заменяет runtime-механизмы SafeStorage.

### 1.3 Raskol Storage Integrity & Maintenance — игровая подсистема

Storage Integrity & Maintenance — отдельная будущая подсистема самого плагина. Её задача — долговременное обслуживание игровых данных во время работы сервера и в предусмотренных lifecycle-окнах.

Она не равна Archivist CI и не является частью RIPS Sentinel:

- RIPS Sentinel защищает JAR, подписи, происхождение и целостность артефакта плагина.
- Archivist CI проверяет корректность реализации storage-кода и миграций в CI.
- Storage Integrity & Maintenance будет проверять и обслуживать игровые данные в runtime.

На момент обновления документа эту подсистему нельзя считать реализованной. Её компоненты описаны ниже как целевая архитектура.

## 2. SafeStorage в main после PR #62

### 2.1 Статус исправления fail-open

Ранее обнаруженный P1-риск относился к старому контракту SafeStorage: при отсутствии читаемой копии метод мог вернуть пустую YAML-конфигурацию, не отличая новое хранилище от повреждённого существующего.

Этот дефект устранён в PR #62. В актуальном main присутствуют:

- LoadStatus: NEW, LOADED_MAIN, RECOVERED_TMP, RECOVERED_BACKUP, CORRUPT и IO_ERROR;
- типизированный LoadResult с конфигурацией, статусом и источником;
- StorageLoadException для CORRUPT и IO_ERROR;
- quarantine повреждённых копий с metadata и SHA-256;
- запрет молчаливого перехода на пустой YAML при повреждении или ошибке доступа;
- запрет перезаписи повреждённого основного файла;
- сохранение оригинальных файлов для диагностики и восстановления.

Следовательно, fail-open — историческая находка исходного аудита, исправленная в main, а не текущее ожидаемое поведение.

### 2.2 Контракт загрузки

SafeStorage.load различает следующие состояния:

| Статус | Значение | Разрешённое поведение |
|---|---|---|
| NEW | Основной файл, .tmp и .bak отсутствуют | Можно начать с пустой конфигурации |
| LOADED_MAIN | Основной YAML прочитан | Использовать основной файл |
| RECOVERED_TMP | Основной файл непригоден, восстановление выполнено из .tmp | Вернуть явный recovery status |
| RECOVERED_BACKUP | Основной файл и .tmp непригодны/отсутствуют, восстановление выполнено из .bak | Вернуть явный recovery status |
| CORRUPT | Существующие копии повреждены | Fail closed; не продолжать с пустым состоянием |
| IO_ERROR | Невозможно проверить или прочитать файлы либо завершить безопасную операцию | Fail closed; не трактовать как NEW или обычную YAML corruption |

Порядок кандидатов: основной файл → .tmp → .bak. Валидный основной файл имеет приоритет. При восстановлении из боковой копии SafeStorage пытается восстановить основной файл. Статус результата позволяет вызывающему коду отличить обычную загрузку от recovery.

Совместимый метод loadWithFallback сохранён для старых call sites, но теперь делегирует типизированной загрузке и выбрасывает StorageLoadException при CORRUPT / IO_ERROR. Совместимость сигнатуры не означает сохранение старой fail-open семантики.

### 2.3 Карантин повреждённых копий

При обнаружении некорректного YAML SafeStorage:

1. Создаёт уникальную quarantine-копию исходного файла.
2. Вычисляет SHA-256 оригинала и копии.
3. Сверяет хеши до продолжения операции.
4. Записывает metadata sidecar с исходным путём, путём карантина, временем, размером, SHA-256 и причиной.
5. Оставляет оригинал на месте; карантин не является удалением или заменой исходника.

Если создать или проверить карантинную копию не удалось, операция завершается fail-closed. Нельзя продолжать запись так, будто повреждённый источник безопасно сохранён.

Карантин не очищается автоматически. Политика retention и GC должна быть отдельной частью Storage Integrity & Maintenance и не входит в SafeStorage.

### 2.4 Безопасная запись

Актуальный saveAtomic:

- валидирует YAML-снимок до commit;
- проверяет состояние существующих основного файла и sidecar-копий;
- не перезаписывает повреждённый основной файл;
- не начинает обычную запись, если основной файл отсутствует, но остались .tmp или .bak, требующие recovery;
- записывает и проверяет временный snapshot;
- перед заменой основного файла обновляет .bak;
- использует обычный move fallback только при AtomicMoveNotSupportedException, а не при любой ошибке I/O.

Ошибку записи нельзя трактовать как подтверждённое сохранение. Вызывающий storage-компонент обязан сохранять dirty state / неподтверждённое поколение до фактического успеха.

## 3. Миграция профилей и специализаций — PR #45

### 3.1 Статус интеграции

PR #45 объединён в main. Единое хранилище `characters.yml` является текущей реализацией, а не только целевым контрактом. В нём совместно хранятся:

- уровень и опыт персонажа;
- основная специализация;
- ранги узлов деревьев специализации;
- ledger обработанных квестовых наград.

`Spec2Storage` остаётся совместимым фасадом для `Spec2Service` и использует единое хранилище профилей; отдельное постоянное хранилище Spec 2.0 больше не является целевым источником истины.

### 3.2 Реализованные источники миграции и приоритеты

Миграция, объединённая в main через PR #45, рассматривает:

- spec2-storage.yml — текущий формат Spec 2.0;
- spec2.yml — legacy-формат;
- соответствующие .tmp и .bak для каждого источника;
- уже существующий characters.yml как приоритетный источник профиля.

Правила объединения:

1. Для каждого старого источника SafeStorage проверяет основной файл, затем .tmp и .bak.
2. При наличии обоих источников spec2-storage.yml имеет приоритет; уникальные legacy-записи из spec2.yml добавляются.
3. При конфликте основной специализации или ранга приоритет остаётся у текущего источника; конфликт фиксируется в логах.
4. Уже существующие данные characters.yml имеют приоритет над обоими источниками. Старые значения добавляются только там, где соответствующие данные отсутствуют.
5. Неизвестная непустая YAML-структура, некорректный UUID, неверный тип поля или некорректный ранг должны останавливать миграцию. Неизвестная структура не считается пустым файлом.

### 3.3 Порядок фиксации и архивации

Реализованный контракт миграции соблюдает следующий безопасный порядок:

1. Прочитать доступные источники с использованием SafeStorage.
2. Проверить структуру и значения источников.
3. Объединить профили и специализации с соблюдением приоритетов.
4. Записать единый characters.yml.
5. Дождаться подтверждения записи через saveAndAwait.
6. Обновить characters.yml.bak полным unified snapshot, включающим специализацию.
7. Только после подтверждения unified snapshot и backup архивировать читаемые legacy-файлы и их .tmp / .bak с суффиксом .migrated.

Если запись unified-файла или обновление его backup не подтверждены, миграция должна остановиться, а исходные источники остаться доступными для повторного запуска или ручного восстановления.

Повреждённый источник не архивируется как успешно мигрированный: его оригинал остаётся на месте, а SafeStorage сохраняет карантинную копию. Если один источник повреждён, но другой содержит пригодные данные, допустимость продолжения определяется проверенными правилами миграции; потерянные данные не должны объявляться перенесёнными.

### 3.4 Что Archivist должен продолжать регрессионно проверять после PR #45

- Round-trip профиля, основной специализации, рангов и quest ledger.
- Приоритет characters.yml над legacy-источниками.
- Приоритет spec2-storage.yml над конфликтующими значениями spec2.yml.
- Объединение уникальных записей из обоих источников.
- Чёткое различие отсутствующего, пустого, повреждённого и неизвестного YAML.
- Восстановление источников из .tmp и .bak через SafeStorage.
- Сохранность оригиналов при CORRUPT / IO_ERROR и при ошибке миграции.
- Отсутствие архивации до успешного saveAndAwait и обновления unified backup.
- Идемпотентность повторного запуска после частично выполненной архивации.
- Отсутствие регрессии SafeStorage из PR #62 при интеграции PR #45.

## 4. Общие инварианты хранения

Эти правила обязательны для всех storage-компонентов:

1. Отсутствие файла и повреждение существующего файла — разные состояния.
2. CORRUPT и IO_ERROR никогда не превращаются в пустое новое хранилище.
3. Ни одна миграция не архивирует источник до подтверждённой записи целевого состояния и необходимых резервных копий.
4. Приоритет источников и правила разрешения конфликтов должны быть явными и покрыты тестами.
5. Неизвестные поля и структуры нельзя безусловно удалять или интерпретировать как пустые данные.
6. Повреждённые исходники, карантин и metadata не удаляются автоматическим процессом.
7. Асинхронный writer получает готовый неизменяемый snapshot; Bukkit API не вызывается из worker thread.
8. Общий AsyncStorageWriter закрывает владелец plugin lifecycle после финальных snapshots, а не отдельный storage-компонент.
9. Ошибка или timeout записи не подтверждают snapshot и не должны сбрасывать dirty state.
10. Диагностика не должна раскрывать содержимое player data.

## 5. Целевая архитектура Raskol Storage Integrity & Maintenance

Это планируемая runtime-подсистема. Её компоненты не следует считать реализованными только потому, что они перечислены в архитектурном документе или проверяются Archivist.

### 5.1 Coordinator

- Координирует обслуживание и безопасный порядок операций.
- Управляет расписанием, блокировками и взаимным исключением обслуживания.
- Не допускает одновременного обслуживания одного набора данных конкурирующими задачами.
- Учитывает lifecycle плагина и активные операции записи.

### 5.2 Compression Engine

- Сжимает и архивирует резервные копии.
- Проверяет целостность созданного архива.
- Подтверждает возможность восстановления из архива тестовым восстановлением в изолированную область.
- Не заменяет оригинальные резервные копии до проверки результата.

### 5.3 Integrity Monitor

- Контролирует состояние основных хранилищ, snapshots, backup и quarantine.
- Проверяет контрольные суммы и выявляет повреждение, пропуски и незавершённые операции.
- Различает отсутствие данных, ошибку доступа, повреждение и устаревший backup.
- Не исправляет неизвестные данные автоматически без безопасной стратегии восстановления.

### 5.4 Garbage Collector

- Выявляет кандидатов на очистку по явным правилам хранения и срокам.
- Перед удалением проверяет, что данные не активны, не являются единственной пригодной копией и не нужны для незавершённой миграции или восстановления.
- Использует безопасный промежуточный карантин/план удаления и журналирует решение.
- Не удаляет quarantine, player data или неизвестные файлы без отдельной подтверждённой политики.

### 5.5 Migration Manager

- Управляет версиями схем и последовательностью миграций.
- Проверяет совместимость источника и целевой схемы.
- Обеспечивает идемпотентность, checkpoint и безопасное повторное выполнение.
- Поддерживает откат или восстановление из подтверждённых backup.
- Не архивирует исходники до завершения всех обязательных шагов.

### 5.6 Diagnostics / Reporting

- Формирует отчёты о состоянии хранилищ.
- Указывает статус загрузки, источник восстановления, контрольные суммы, quarantine path и незавершённые записи.
- Показывает состояние backup и миграций, а также причину отказа.
- Не включает содержимое профилей, UUID-ориентированные персональные значения или секреты в общие диагностические отчёты без необходимости.

### 5.7 Граница с Archivist CI

Archivist проверяет реализацию каждого компонента Storage Integrity & Maintenance, тестирует его правила на изолированных данных и блокирует регрессии. Он не исполняет maintenance-операции над production player data.

## 6. План развития и контрольные этапы

1. **Зафиксировать runtime-базу:** SafeStorage fail-closed из PR #62 остаётся обязательной основой.
2. **Поддерживать интеграцию профиля:** PR #45 уже объединён; сохранять регрессионное покрытие unified storage, миграций, backup/restore и совместимого фасада Spec2Storage.
3. **Развить Archivist CI:** добавить отдельные сценарии SafeStorage, migration, backup/restore, quarantine и writer lifecycle; отчёт должен показывать проверенные гарантии.
4. **Спроектировать Storage Integrity & Maintenance:** определить API, lifecycle, форматы отчётов, расписание и блокировки до написания runtime-кода.
5. **Реализовать подсистему по компонентам:** Coordinator → Integrity Monitor → Migration Manager → Compression Engine → Diagnostics → безопасная политика Garbage Collector.
6. **Проверить runtime:** unit/integration tests, затем Paper 26.2 runtime QA на изолированном тестовом сервере.
7. **Включать автоматическое обслуживание только после доказанной возможности восстановления:** GC и retention не должны запускаться раньше проверки backup/restore и политики карантина.

## 7. Минимальная матрица проверок Archivist

| Область | Обязательные сценарии |
|---|---|
| SafeStorage load | NEW; LOADED_MAIN; RECOVERED_TMP; RECOVERED_BACKUP; CORRUPT; IO_ERROR |
| Приоритет копий | Валидный main побеждает sidecar; валидный .tmp используется раньше .bak |
| Quarantine | Повреждённая копия сохраняется; SHA-256 совпадает; metadata создана; оригинал не удалён |
| Fail closed | CORRUPT / IO_ERROR не возвращают пустую конфигурацию и не разрешают последующую перезапись |
| Atomic save | Валидация snapshot; обновление backup; fallback только при AtomicMoveNotSupportedException |
| Migration | Current + legacy; конфликтующие и уникальные записи; неизвестная структура; повреждённые источники |
| Migration commit | saveAndAwait → unified backup → archive; отказ на каждом шаге сохраняет источники |
| Recovery | Повторный запуск после частичной миграции; восстановление из .tmp / .bak; проверка byte-for-byte сохранности источников |
| Writer lifecycle | Saturation; timeout; interruption; active write during shutdown; завершение queued futures |
| Reporting | Статусы и причины без вывода содержимого игровых данных |

Все CI-тесты, миграционные fixtures и проверки восстановления должны работать на временных каталогах и тестовых данных. Запуск CI не должен иметь доступа к реальным player data сервера.

## 8. Границы этого документа и PR #60

PR #60 остаётся документационным этапом Archivist. В рамках него:

- актуализируется архитектурная документация с учётом PR #62;
- фиксируется уже объединённая миграция профилей/специализаций из PR #45;
- описывается контракт восстановления .tmp / .bak и карантина;
- разделяются Archivist CI и будущая Storage Integrity & Maintenance;
- не меняются production storage-код, YAML игроков, схемы, игровые данные и runtime lifecycle.

PR #45 уже объединён и его storage-код находится в main. Этот документ не является доказательством реализации Storage Integrity & Maintenance: её статус меняется только после соответствующих изменений, проверок и отдельного подтверждения в GitHub.
