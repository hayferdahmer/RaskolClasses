## Назначение

Burst budget должен учитывать только фактически использованный урон. Откат одной отменённой или частично применённой атаки не должен менять бюджет соседней атаки.

## Модель

`BurstReservationLedger` хранит отдельную запись на каждую резервацию. Каждая запись представлена уникальным `Token` и содержит timestamp и остаток зарезервированного бюджета.

- `reserveBurstCap` рассчитывает доступную часть burst-лимита и возвращает пару `allowed + token`.
- `rollbackBurst` уменьшает только запись Path A, на которую указывает token.
- `settleBurst` через reconciliation устанавливает точный фактический расход Path B.
- Повторный rollback безопасен: остаток не может стать отрицательным, исчерпанный token удаляется.
- Истёкшие записи удаляются по временному окну.
- Откат не ищет «последнюю запись» и не зависит от порядка вложенных атак.

## Path A — Vanilla/Paper event

На NORMAL listener создаётся reservation и связывается с точным экземпляром `EntityDamageEvent` в `BurstRollbackTracker`.

На MONITOR listener:
- если событие не отменено — reservation остаётся учтённой;
- если событие отменено — откатывается только token этого события.

## Path B — CombatService

Path B резервирует общий бюджет до разделения на физический и магический Paper events. После каждого синхронного `target.damage(...)` сравнивается HP до и после вызова.

Физический и магический вызовы измеряются отдельно через `DamageAttribution`, но общий token урегулируется ровно один раз после завершения обоих каналов:

- фактические health delta каналов переводятся в formula units и суммируются;
- `BurstReservationLedger.reconcile(token, actual)` приводит запись к точному фактическому расходу;
- при меньшем уроне неиспользованный резерв освобождается;
- при увеличении урона запись расширяется до фактического расхода, даже если он превышает исходный резерв;
- отменённый канал даёт нулевой health delta;
- если канал не завершился из-за исключения, его фактический результат остаётся нулевым, а общий settlement в `finally` сохраняет только уже применённый урон.

Таким образом, settlement не ограничен исходным размером резерва и не принимает отправленный в Paper amount за доказательство применённого урона.

## Реентерабельный Path B — вложенные вызовы

Before/after health delta одного вызова `Entity.damage(...)` может включать урон, нанесённый синхронным вложенным `CombatService.dealDamage(...)` из обработчика Paper event. Поэтому одного сравнения HP недостаточно для атрибуции конкретному каналу.

`DamageAttribution` открывает thread-local LIFO scope на каждый физический или магический вызов Paper. При завершении scope:
- измеряется общий net health delta этого вызова;
- из собственного результата вычитается net delta вложенных scope для того же экземпляра цели;
- полный net delta дочернего вызова передаётся ближайшему родительскому scope той же цели, чтобы исключить его из родительского измерения;
- вложенные вызовы по другой цели не влияют на текущую атрибуцию;
- scope закрывается в `finally`, в том числе при исключении из Paper damage call.

Это не меняет расчёт урона или порядок каналов. Меняется только то, как фактический HP delta распределяется между вызовами перед урегулированием их reservation token.

## Инварианты и тесты

- Отмена старого события не может снять reservation более позднего события.
- Физическая и магическая части одной Path B атаки измеряются отдельно, но общий token урегулируется один раз.
- Path A rollback ограничен остатком своего token и идемпотентен.
- Path B reconciliation меняет только свой token и допускает фактический расход выше первоначального резерва.
- Истечение окна освобождает старые записи.
- Отключённый burst cap не создаёт token и не требует rollback.

Unit coverage:
- `BurstReservationLedgerTest` — бюджет, независимые token, частичный rollback, expiry, увеличение/уменьшение фактического расхода, нулевой settlement и невалидные/чужие token.
- `DamageAttributionTest` — вложенность в несколько уровней, собственный/вложенный урон, другая цель, соседние вложенные вызовы, отменённый вызов и LIFO-контракт.
- `BurstRollbackTrackerTest` — привязка по identity события и защита соседних reservation.

## Paper 26.2 runtime-проверка

В PR #78 добавлен отдельный Watchtower fixture с реальным подключённым Bukkit Player. Он проверяет отмену физического канала, отмену магического канала, отмену обоих каналов и вложенный удар во время обработки внешнего события.

Для каждого сценария сверяются Paper event causes, состояние отмены, фактическое изменение здоровья и остаток burst ledger. Дополнительные сценарии увеличивают и уменьшают физический event damage, проверяя расширение и освобождение общего token. Runtime-результат считается подтверждённым только после прохождения CI на одном и том же HEAD follow-up.

## Границы

Это не изменение формул или значений баланса. Path A сохраняет текущую точку резервирования после модификаторов listener. Path B сохраняет существующий порядок физического и магического вызова. Unit-тесты и runtime matrix дополняют друг друга, но не доказывают полную Path A/Path B parity.
