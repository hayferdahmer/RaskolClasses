## Назначение

Burst budget должен учитывать только фактически использованный урон. Откат одной отменённой или частично применённой атаки не должен менять бюджет соседней атаки.

## Модель

`BurstReservationLedger` хранит отдельную запись на каждую резервацию. Каждая запись представлена уникальным `Token` и содержит timestamp и остаток зарезервированного бюджета.

- `reserveBurstCap` рассчитывает доступную часть burst-лимита и возвращает пару `allowed + token`.
- `rollbackBurst` уменьшает только запись, на которую указывает token.
- Повторный rollback безопасен: остаток не может стать отрицательным, исчерпанный token удаляется.
- Истёкшие записи удаляются по временному окну.
- Откат не ищет «последнюю запись» и не зависит от порядка вложенных атак.

## Path A — Vanilla/Paper event settlement

На NORMAL listener создаётся reservation и связывается с точным экземпляром `EntityDamageEvent` через одноразовый `BurstRollbackTracker.Handle`. Handle хранит player UUID, token, исходный размер резервации, scale и время создания.

На MONITOR listener:

- отменённое событие откатывает только собственный handle;
- успешное событие выполняет settlement по итоговому `event.getDamage() / scale`;
- уменьшение урона освобождает разницу;
- увеличение урона учитывается полностью, даже если итоговый расход окна превысит cap; превышение отдельно диагностируется;
- невалидный итоговый урон (`NaN`, бесконечность или отрицательное значение) не меняет ledger: сохраняется исходная резервация и записывается предупреждение;
- handle закрывается ровно один раз, повторное завершение не меняет ledger.

MONITOR не изменяет Paper event. Settlement читает его состояние и меняет только ledger. Отдельная периодическая очистка откатывает handle, которые не были завершены в течение 30 секунд, чтобы не удерживать event references и не оставлять незакрытые резервации.

Paper определяет EventPriority.MONITOR как точку наблюдения: обработчики этого приоритета не должны изменять событие. Если сторонний плагин всё же меняет damage в более позднем MONITOR listener, RaskolClasses не может гарантировать, что settlement увидел последнее значение. Для сторонних изменений на NORMAL/HIGH/HIGHEST итоговое значение будет учтено.

## Path B — CombatService settlement

Path B резервирует общий бюджет до разделения на физический и магический Paper events. После каждого синхронного `target.damage(...)` фактический health delta относится к соответствующему вызову, а не к сумме всех вложенных вызовов.

Для каждой части отдельно:

- фактический урон в formula units остаётся учтённым;
- неиспользованный остаток reservation возвращается;
- если событие отменено, health delta равен нулю и соответствующая часть возвращается;
- если второй вызов не выполнен из-за исключения, его резерв полностью освобождается в `finally`.

### Реентерабельная атрибуция

Before/after health delta одного вызова `Entity.damage(...)` может включать урон, нанесённый синхронным вложенным `CombatService.dealDamage(...)` из обработчика Paper event. Поэтому одного сравнения HP недостаточно для атрибуции конкретному каналу.

`DamageAttribution` открывает thread-local LIFO scope на каждый физический или магический вызов Paper. При завершении scope:

- измеряется общий net health delta этого вызова;
- из собственного результата вычитается net delta вложенных scope для того же экземпляра цели;
- полный net delta дочернего вызова передаётся ближайшему родительскому scope той же цели, чтобы исключить его из родительского измерения;
- вложенные вызовы по другой цели не влияют на текущую атрибуцию;
- scope закрывается в `finally`, в том числе при исключении из Paper damage call.

Это не меняет формулы урона или порядок каналов. Меняется только распределение фактического HP delta между вызовами перед урегулированием их reservation token.

## Paper 26.2 runtime matrix

Watchtower запускает обе матрицы последовательно на одном подключённом Bukkit Player в изолированном Paper 26.2 CI:

1. **Path B** — четыре сценария реального hybrid damage:
   - отмена физического `ENTITY_ATTACK` при успешном магическом канале;
   - отмена магического канала при успешном физическом;
   - отмена обоих каналов;
   - вложенный hybrid hit во время внешнего физического события с отменой только внешнего физического канала.
2. **Path A** — четыре синтетических Player-target `EntityDamageEvent`, отправленных через Paper PluginManager:
   - внешний listener уменьшает damage после NORMAL — ledger освобождает разницу;
   - внешний listener увеличивает damage после NORMAL — ledger учитывает превышение и пишет диагностику;
   - вложенное событие проходит, внешнее отменяется — сохраняется только вложенная резервация;
   - вложенное и внешнее события проходят, внешний damage изменяется — обе резервации независимо отражают финальные значения.

Path B проверяет реальные Paper damage calls, здоровье Player и ledger. Path A проверяет production event listeners и settlement ledger, но не NMS-применение урона к здоровью: события создаются и синхронно отправляются через PluginManager.

Обе матрицы используют общую инициализацию и временные лимиты только в памяти тестового сервера. Path B выполняется первым; Path A стартует после его итогового PASS. Единая финальная очистка восстанавливает исходные значения конфигурации в памяти, удаляет тестового моба и отключает тестового Player. При ошибке любого этапа выполняется та же очистка.

Workflow требует четыре PASS-записи каждого набора сценариев и итоговые маркеры:

- `SUPPRESS_SCOPE_PASS`
- `BURST_CANCELLATION_MATRIX_PASS`
- `PATH_A_SETTLEMENT_MATRIX_PASS`

Для Path A дополнительно проверяется диагностическое сообщение об увеличении урона после reserve. Любой fail-маркер или неполная матрица блокирует Watchtower.

## Инварианты и тесты

- Отмена старого события не может снять reservation более позднего события.
- Физическая и магическая части одной Path B атаки могут урегулироваться независимо.
- Rollback ограничен остатком своего token и идемпотентен.
- Истечение окна освобождает старые записи.
- Отключённый burst cap не создаёт token и не требует rollback.

Unit coverage:

- `BurstReservationLedgerTest` — бюджет, независимые token, частичный rollback, expiry и невалидные значения.
- `BurstRollbackTrackerTest` — привязка по identity события и защита соседних reservation.
- `DamageAttributionTest` — вложенность в несколько уровней, собственный/вложенный урон, другая цель, соседние вложенные вызовы, отменённый вызов и LIFO-контракт.

## Границы

Это не изменение формул или значений баланса. Path A сохраняет settlement после модификаторов listener. Path B сохраняет существующий порядок физического и магического вызова. Runtime QA выполняется только на изолированном CI Paper 26.2 и не является запуском на production RASKOL.
