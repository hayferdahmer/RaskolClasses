## Назначение

Burst budget должен учитывать только фактически использованный урон. Откат одной отменённой или частично применённой атаки не должен менять бюджет соседней атаки.

## Модель

`BurstReservationLedger` хранит отдельную запись на каждую резервацию. Каждая запись представлена уникальным `Token` и содержит timestamp и остаток зарезервированного бюджета.

- `reserveBurstCap` рассчитывает доступную часть burst-лимита и возвращает пару `allowed + token`.
- `rollbackBurst` изменяет только запись Path A, на которую указывает точный event-bound handle/token.
- `settleBurst` урегулирует общий token Path B по фактическому суммарному расходу физических и магических каналов.
- Повторный rollback безопасен: остаток не может стать отрицательным, исчерпанный token удаляется.
- Истёкшие записи удаляются по временному окну.
- Операции не ищут «последнюю запись» и не зависят от порядка вложенных атак.

## Path A — Vanilla/Paper event settlement

На NORMAL listener создаётся reservation и связывается с точным экземпляром `EntityDamageEvent` через одноразовый `BurstRollbackTracker.Handle`. Handle хранит player UUID, token, исходный размер резервации, scale и время создания.

На MONITOR listener:

- отменённое событие откатывает только собственный handle;
- успешное событие выполняет settlement по итоговому `event.getDamage() / scale`;
- уменьшение урона освобождает разницу;
- увеличение урона учитывается полностью, даже если итоговый расход окна превысит cap; превышение отдельно диагностируется;
- невалидный итоговый урон (`NaN`, бесконечность или отрицательное значение) не меняет ledger: сохраняется исходная резервация и записывается предупреждение;
- handle закрывается ровно один раз, повторное завершение не меняет ledger.

MONITOR не изменяет Paper event. Settlement читает его состояние и меняет только ledger. Отдельная периодическая очистка откатывает handle, которые не были завершены в течение 30 секунд, чтобы не удерживать event references и не оставлять незакрытые резервации.

Paper определяет EventPriority.MONITOR как точку наблюдения: обработчики этого приоритета не должны изменять событие. Если сторонний плагин всё же меняет damage в более позднем MONITOR listener, RaskolClasses не может гарантировать, что settlement увидел последнее значение. Для сторонних изменений на NORMAL/HIGH/HIGHEST итоговое значение будет учтено.

## Path B — CombatService settlement

Path B резервирует общий burst budget одним token до разделения атаки на физический и магический Paper events. Физический и магический вызовы измеряются отдельно через существующий `DamageAttribution`, но общий token урегулируется ровно один раз после завершения обоих каналов.

- Фактические изменения защитного пула (health + absorption) каналов переводятся в formula units и суммируются.
- `BurstReservationLedger.settle(token, actual)` приводит запись к точному фактическому расходу и возвращает исходную сумму, итоговую сумму и overage.
- При меньшем уроне неиспользованный резерв освобождается.
- При увеличении урона запись расширяется до фактического расхода, даже если он превышает исходный резерв; overage остаётся доступен для диагностики.
- Отменённый канал даёт нулевое изменение защитного пула.
- Если вызов канала завершается исключением, `DamageAttribution` всё равно закрывается в `finally` и фиксирует фактический net defensive-pool delta, уже произошедший до исключения; если защитный пул не изменился, вклад канала равен нулю.
- Внешний `finally` урегулирует общий token по сумме измеренных каналов даже при исключении.

Таким образом, settlement не ограничен исходным размером резерва и не принимает отправленный в Paper amount за доказательство применённого урона.

### Реентерабельная атрибуция

Before/after defensive-pool delta одного вызова `Entity.damage(...)` может включать урон, нанесённый синхронным вложенным `CombatService.dealDamage(...)` из обработчика Paper event. Поэтому одного сравнения HP недостаточно для атрибуции конкретному каналу.

`DamageAttribution` открывает thread-local LIFO scope на каждый физический или магический вызов Paper. При завершении scope:

- измеряется общий net defensive-pool delta этого вызова;
- из собственного результата вычитается net delta вложенных scope для того же экземпляра цели;
- полный net delta дочернего вызова передаётся ближайшему родительскому scope той же цели, чтобы исключить его из родительского измерения;
- вложенные вызовы по другой цели не влияют на текущую атрибуцию;
- scope закрывается в `finally`, в том числе при исключении из Paper damage call.

Это не меняет формулы урона или порядок каналов. Меняется только распределение фактического HP delta между вызовами перед урегулированием их reservation token.

## Paper 26.2 runtime matrix

Watchtower запускает последовательные проверки на одном подключённом Bukkit Player в изолированном Paper 26.2 CI:

1. **Path B** — семь сценариев реального damage:
   - отмена физического `ENTITY_ATTACK` при успешном магическом канале;
   - отмена магического канала при успешном физическом;
   - отмена обоих каналов;
   - вложенный hybrid hit во время внешнего физического события с отменой только внешнего физического канала;
   - увеличение physical event damage внешним listener с проверкой расширения общего token;
   - уменьшение physical event damage внешним listener с проверкой освобождения неиспользованного резерва;
   - полный absorption-only hit: здоровье не меняется, но расход поглощения учитывается в settlement.
2. **Warlock Black Mass** — вложенный реальный урон проверяет сохранение UUID источника способности на обоих событиях и соответствие фактического lifesteal сумме вкладов MONITOR.
3. **Path A** — четыре синтетических Player-target `EntityDamageEvent`, отправленных через Paper PluginManager:
   - внешний listener уменьшает damage после NORMAL — ledger освобождает разницу;
   - внешний listener увеличивает damage после NORMAL — ledger учитывает превышение и пишет диагностику;
   - вложенное событие проходит, внешнее отменяется — сохраняется только вложенная резервация;
   - вложенное и внешнее события проходят, внешний damage изменяется — обе резервации независимо отражают финальные значения.

Path B проверяет реальные Paper damage calls, защитный пул Player (здоровье + поглощение) и ledger. Path A проверяет production event listeners и settlement ledger, но не NMS-применение урона к здоровью: события создаются и синхронно отправляются через PluginManager.

Обе матрицы используют общую инициализацию и временные лимиты только в памяти тестового сервера. Path B выполняется первым; затем проходит Warlock Black Mass nested-context probe; Path A стартует только после его PASS. Единая финальная очистка восстанавливает исходные значения конфигурации в памяти, восстанавливает class-cache entry, удаляет тестовых мобов и отключает тестового Player. При ошибке любого этапа выполняется та же очистка.

Workflow требует семь PASS-записей Path B, четыре PASS-записи Path A и итоговые маркеры:

- `SUPPRESS_SCOPE_PASS`
- `PATH_B_SETTLEMENT_MATRIX_PASS`
- `BURST_CANCELLATION_MATRIX_PASS`
- `BLACK_MASS_NESTED_CONTEXT_PASS`
- `PATH_A_SETTLEMENT_MATRIX_PASS`

Для Path A дополнительно проверяется диагностическое сообщение об увеличении урона после reserve. Любой fail-маркер или неполная матрица блокирует Watchtower.

## Инварианты и тесты

- Отмена старого события не может снять reservation более позднего события.
- Физическая и магическая части одной Path B атаки измеряются отдельно, но общий token урегулируется один раз.
- Path A rollback ограничен остатком своего token и идемпотентен.
- Path B settlement меняет только свой token, допускает фактический расход выше первоначального резерва и возвращает overage для предупреждения.
- Истечение окна освобождает старые записи.
- Отключённый burst cap не создаёт token и не требует rollback.

Unit coverage:

- `BurstReservationLedgerTest` — бюджет, независимые token, частичный rollback, expiry, увеличение/уменьшение фактического расхода, диагностика overage, нулевой settlement, невалидные/чужие token и settlement после исключения с частичным либо нулевым defensive-pool delta.
- `BurstRollbackTrackerTest` — привязка по identity события и защита соседних reservation.
- `DamageAttributionTest` — вложенность в несколько уровней, собственный/вложенный урон, другая цель, соседние вложенные вызовы, отменённый вызов, полное/частичное поглощение и LIFO-контракт.

## Границы

Это не изменение формул или значений баланса. Path A сохраняет settlement после модификаторов listener. Path B сохраняет существующий порядок физического и магического вызова; изменено только измерение фактически применённого урона с учётом поглощения. Runtime QA выполняется только на изолированном CI Paper 26.2 и не является запуском на production RASKOL.
